## 测试方法

- Windows 10，Python 3.10.20，16 个物理核心 / 32 个逻辑处理器，15.2 GB 内存。
- 单 Uvicorn worker；客户端与服务端同机，通过真实 loopback HTTP 调用。
- 真实登录和 CSRF 校验；每个虚拟用户使用独立客户端，共用同一个合成测试账号的认证会话。
- 每档持续发起请求 15 秒，结束后等待在途请求完成；RPS 用完成请求数除以包含排空时间的总耗时。
- 闭环并发、零思考时间，每个虚拟用户最多一个在途请求；不是固定到达率压测。
- 登录和模型预热不计入阶段延迟；实际执行上传、解码、质检、字段解析、规则判定和 SQLite 落库。
- 大模型服务关闭。mock 数字不代表真实 OCR 性能；Paddle 强制使用 CPU，不代表 GPU 性能。
- 使用独立临时端口、独立 SQLite 数据库、合成图片；业务源代码未为本次压测做性能修改。
- 成功除了 HTTP 200，还检查字段、OCR 文本、审核结论及原因与预热结果一致，并检查 request_id 唯一。

## 发现的问题

1. SQLite 写入竞争已复现。标准图 40 并发失败 23/896，80 并发失败 23/892；包含 HTTP 500 和读取断连。服务端日志记录 sqlite3.OperationalError: database is locked。成功响应没有发现缺失记录；不能由此推断失败请求也有完整审计记录。
2. Paddle CPU 吞吐约 0.16–0.17 次/秒，增加并发主要增加排队。当前共享推理实例被全局锁串行保护；8 并发 P95 约 50.62 秒。实际复测只完成 23 个测量请求，尾部指标样本量很小，不应当作长期容量保证。
3. 首次真实 Paddle 测试预热成功，但进入单并发阶段后服务进程异常退出，7 次测量尝试全部失败；中止后续阶段。第一次未记录进程退出码，不能据此确定退出根因。
4. 加入故障诊断输出后，低并发复核的两次请求通过，随后完整 1/2/4/8 并发复测也完成。完整复测日志仍记录 Windows fatal exception: access violation，位于 PaddleX 原生推理调用附近；该轮进程随后仍返回成功请求，因此日志不能单独证明进程已退出。真实 CPU 路径存在需要进一步定位的稳定性风险。
5. 10 并发标准图 mock 档本次无失败且 P95 约 251 ms；这只是本次短窗口观测，未验证长时间稳定性或真实用户分布。
