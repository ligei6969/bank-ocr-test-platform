# 面试项目介绍：约五分钟口述稿

按每分钟约 280–320 字、配合停顿练习。正文口述时，接口路径可用中文功能名称代替。涉及个人负责范围的表述，应按自己的实际参与情况调整。

## 口述正文

面试官您好，我介绍的项目是银行证件 OCR 自动化测试平台。它模拟银行材料提交与人工复核场景，支持银行卡和身份证图片审核，并加入 AI 解释、知识问答，以及持续测试演进能力。我希望通过这个项目解决两个问题：一是识别结果怎样转成可追溯的业务结论，二是怎样测试输出存在不确定性的 AI 系统。

先介绍业务流程。用户登录后上传图片，系统依次完成文件校验、图像质检、OCR、字段解析和规则审核，返回通过、待人工复核、拒绝或处理错误，并保存审核记录。银行卡主要提取卡号、姓名和有效期；身份证支持正反面信息解析。管理端可以查询记录，查看审核原因和 AI 的处置建议。

架构上，我把系统分成三层。第一层是 FastAPI 审核平台，负责上传、鉴权、质检和规则；第二层是独立 AI 服务，负责检索、解释和受限工具决策；第三层是测试与评测层，负责自动化回归、模型行为评测和经验管理。当前用 SQLite 保存审核记录，适合本机演示和验证。

接口方面，平台有银行卡审核、身份证审核、审核记录列表和详情查询，以及 AI 解释和 Agent 解释接口。两个主要上传接口是 POST /bank-card/review 和 POST /id-card/review。独立 AI 服务还有知识问答、边界复核、检索和健康检查接口。按 HTTP 方法和路径统计，连同页面、认证和运维入口，共有二十七个接口。

图片质检采用 OpenCV 指标和规则：用拉普拉斯方差判断模糊，用灰度均值判断亮暗，用 HSV 和连通区域检测反光，再根据文字区域方向判断倾斜、根据深色区域形态发现疑似遮挡。一般质量问题转人工，严重退化按规则拒绝。这些阈值依据项目样本标定，换真实业务数据还需要重新验证。

AI 部分的关键设计是明确权限和失败处理。规则的拒绝结论不能被模型改成通过，倾斜等影像证据也不能被文本解释消除。发送给 AI 的姓名和证件号码会脱敏，工具调用受白名单、参数校验、步数和 token 预算约束。平台侧还有超时、熔断和降级，AI 不可用时保留规则结论。安全上重点防范记录越权、恶意上传和隐私泄露，因此加入角色权限、CSRF、图片内容校验和日志脱敏。

对于不确定的 AI，我分层测试。接口、解析器和业务规则用 pytest 做确定性验证；模型部分既检查答案依据，也检查工具、参数、预算和停止原因。固定交互通过录制回放进入回归，真实模型质量另用独立数据和重复采样评估。比如模型没有回答，不能直接算安全测试通过，还要确认它是否正确识别了应该拒绝的请求。

在此基础上，我加入了 CTE，也就是持续测试演进：利用已验证经验提出新缺陷假设，冻结预测，再执行测试、独立判定，最后通过人工审核更新经验。预测器看不到当前答案，判定器不接收预测理由；未验证经验不能进入默认检索。第一版已经跑通工程流程，后续还需要独立实验验证经验是否提高了未知缺陷发现能力。

测试中有几个具体发现。一个是解析器把有效期标签误选为持卡人姓名，修复后，在一百张合成模糊卡的真实 OCR 文本回放中，姓名正确数从四十八提高到五十五；七百张回放中，没有发现原本正确的姓名回退。另一个是客服评测存在“假通过”：部分应拒问题只是因为找不到知识而未回答。我收紧了判据，分别检查拒答原因和话术，避免用最终没泄露掩盖识别错误。

性能方面，我也做了真实 HTTP 压测，包含登录、CSRF、上传、审核和落库。mock OCR 下，标准图片十并发约每秒五十九次、没有失败；四十和八十并发一度出现约百分之二点六的失败，日志定位到 SQLite 写锁竞争。查下来根因是每次落库前都会重跑一遍建表与建索引语句，几十个线程同时抢写锁。我把建库改成每个库文件只执行一次、写连接在进程内排队，并启用 WAL，用同一个脚本、同一批档位复测，失败从七十三个降到零，四十并发吞吐提高约四成、P95 从五秒降到七百毫秒。真实 GPU 测试使用 RTX 4070，四并发约每秒九点三次，P95 约四百五十一毫秒；整组五百二十二次请求全部成功并核对落库。但这是短时、本机数据，不能作为生产容量保证。

成果方面，最近一次完整回归是一千五百八十一项通过，其中 CTE 专项一百六十八项通过。项目形成了从审核、异常定位到回归资产积累的流程。单进程的数据库写锁竞争已经修复并复测为零失败，但多进程部署和 OCR 排队问题仍未解决，CPU 推理也曾出现进程异常退出，根因还在定位。真实客户数据和长期压力测试需要继续补充。这个项目让我更明确地理解了测试开发：理解业务风险，用代码建立可验证的判据，让问题能定位、修复效果能比较、历史缺陷能持续回归。
