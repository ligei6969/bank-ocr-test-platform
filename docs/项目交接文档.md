## 零、30 秒了解这个项目

一个银行影像（银行卡/身份证）审核测试平台。平台侧是确定性的 FastAPI 服务
（OCR → 质量检测 → 字段解析 → 规则 → 落库），上面叠了一层**独立进程的 AI 能力层**
（审核解释、知识客服、规则+LLM 双判），再上面是一套**测试资产演进机制（CTE）**。

**真正的立意不在审核业务本身**（那部分是确定性的，传统接口测试够用），
而在于回答：**一个会调工具、多步决策、输出不确定的 AI 系统，要怎么测。**

## 一、先把环境跑起来

### 1.1 Python 环境

项目用 conda 环境 `bank`：

```bash
conda activate bank
python -m pip install -r requirements.txt
```

**Windows 上跑测试要加一个环境变量**（沙箱 teardown 会报 `SHFileOperationW`，
与本项目代码无关）：

```bash
CODEBUDDY_SAFE_DELETE_ENABLED=0 python -m pytest -q
```

### 1.2 三个入口，都验证过能跑

```bash
# 平台服务（默认 mock OCR，不需要模型）
python -m uvicorn app.main:app --host 127.0.0.1 --port 8001
#   → http://127.0.0.1:8001/           审核页
#   → http://127.0.0.1:8001/docs       Swagger
#   → http://127.0.0.1:8001/bank-card/ui

# AI 能力层（独立进程，默认 127.0.0.1:8100）
python -m ai_service                    # 起服务
python -m ai_service --demo             # 自检：不联网跑完整链路
python -m ai_service --agent            # 审核 Agent 路径，打印轨迹/预算/token
python -m ai_service --ask "办理二类账户需要哪些材料"

# 全量测试（约 85 秒）
python -m pytest -q                     # 期望 1534 passed
```

**不启动 AI 服务平台照常工作** —— AI 不可用时审核链路不受影响，只是没有解释面板。

### 1.3 不需要任何 API key

没配 key 时自动走确定性策略，**降级只损失措辞，事实内容完全不变**。
真实模型只在显式加 `--live` 时才调用。

## 三、必须知道的五条设计立场

这五条是整个项目的骨架。改动前先读它们，否则很容易把设计当成 bug 修掉。

### 1. AI 是独立进程，不是平台的一部分

平台挂了要照常工作，AI 挂了也要照常工作。走 HTTP，有超时 + 三态熔断 + 降级。
**不要为了省事把 AI 逻辑内联进 `app/`。**

### 2. 规则拥有否决权，LLM 只有有限的放行建议权

`app/adjudication.py` + `ai_service/adjudication.py`。
核心不变式：**任何失败都回落规则原判**。
`Literal["review","pass"]` 让模型**结构上产不出** `reject`。

### 3. 事实与措辞分离

事实来自语料（`corpus.py`），模型只组织措辞。
所以「没配 key」时降级只损失表达，**不损失准确性**。

### 4. 白名单是硬约束，参数在派发**之前**校验

模型说调什么不算数，注册表里没有就拒绝。

### 5. 全量测试离线可跑，CI 不加载 PaddleOCR

真实模型只在 `--live`；真实 OCR 只在独立 job 或本地录制脚本。
**默认路径绝不出网。**

## 四、常见坑（都踩过）

### 坑 1：CI 会删掉一部分测试图

`.github/workflows/tests.yml` 的清理步骤只保留每类前 3 张银行卡图。
golden 集每桶取 4 张 —— 所以 CI 里有些样本的图是不在的。

**这就是为什么评测要读 OCR 快照而不是现读图。**
如果你新增了依赖图片的评测逻辑，先想清楚 CI 里那张图还在不在。

实测：移走图后，不用快照 5/40 条拿不到质量数据，用快照 0/40。

### 坑 2：名称叫「严重度优先」的测试，可能没在测它

`tests/test_rule_check.py` 里曾有一条 `test_missing_fields_still_outrank_severity`，
docstring 写「严重度判拒也要带上原因码」，断言却只检查 `missing_card_number` 在不在 ——
于是它为一个**丢弃严重度**的实现背了很久的书。

> **教训：断言要检查 docstring 承诺的那件事。**

### 坑 3：长任务必须能续

录 2100 张 OCR 要跑近半小时，而 PaddleOCR 在长循环里会崩
（实测 `CUDA error(700) illegal memory access`）。
初版攒在内存最后才写 —— **半小时成果全丢**。

现在边录边写 + 断点续录（`--restart` 可强制重来）。

### 坑 4：mock OCR 的形状是「设计出来的」，不是「观察到的」

`MOCK_OCR_TEXT` 把「姓名 沈梓欣」拼成一行，而真实 PaddleOCR 检测成
**两个独立文本框**。实现与测试共享这个假设，一起错、测不出差异 ——
真实形状下身份证字段解析曾经 **0/10**。

**新增解析逻辑时，用 `data/annotations/ocr_outputs.json` 里的真实文本行做输入**，
不要只用 mock 形状。

### 坑 5：不要靠调参解决没有度量的问题

反光严重度阈值至今**停用**（`SEVERE_GLARE_COMPONENT_RATIO_THRESHOLD = None`），
因为当初的标定间隙只有 9%，据此判拒绝属于过拟合。

**在 CTE-5 给出全量分布之前，调它无法验证对错。**
现在有了依据（`docs/ocr_field_error_rates.md`），但启用它仍是**产品口径决策**。

按「是否需要外部输入」分成两类。

### A. 本轮已收口的纯工程项

| # | 事项 | 说明 |
| --- | --- | --- |
| 1 | **P4b MCP server** | 已以 stdio 暴露 `review_explain` / `knowledge_ask`；不开额外网络端口 |

| 3 | pytest 临时目录 | 每次运行使用独立目录，避免 Windows 残留 ACL 让全量验收误报 |

### B. 需要外部输入（做不了技术决定）

| # | 事项 | 等什么 |
| --- | --- | --- |
| 1 | 反光严重度阈值启用 | **产品口径**：什么样的反光算不可用。CTE-5 已给出分布 |
| 2 | 4 条过度保守的 `pass→review` | 阈值标定，同上 |
| 3 | 对外化 R1–R3（无认证/无限流/响应含内部信息） | 产品决策，不只是技术 |
| 4 | 真实证件照片 | 隐私合规采集；当前全是合成数据 |

### C. 明确不建议做的

- ❌ **继续在合成数据上调阈值** —— 调了也无法验证对错
- ❌ **双判改判正确性的标定** —— 反光阈值未定会把问题混进双判指标
- ❌ **加 Agent 面 / 加仪表盘** —— 边际价值已很低

## 七、EVT-006 / EVT-007 修复与剩余边界

EVT-006 已按用户确定的方向修复：有限模糊有效期标签、附近日期证据、持卡人标签及卡号位置评分。700 张银行卡 OCR 快照比较：正常姓名 100/100；模糊姓名 48/100 → 55/100；没有原本正确的姓名回退。OCR 原文、标注和评测基线未修改。残余漏字、粘连与严重损坏不能保证由解析器修复。

EVT-007 修复客服评测假绿：旧规则 + 新判据复现错闸门率 9/30=30%、话术缺失率 30%；当前 45 题严格通过，30 条应拒全部走 refused。新指标 wrong_gate_refusal_rate 与漏拒率独立呈现。

CTE-003/006/007 已完成机器验证，均无人工签名；validated 仍为原来的 4 条。完整证据见 [审查问题修复验证](审查问题修复验证.md)。
