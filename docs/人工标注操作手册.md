# 人工标注操作手册

这份手册解决一件事：**评测里唯一必须由人产出的输入，怎么用最小的人工量做出来。**

结论先说：**你要手工填的只有一列 —— `expected_verdict`，40 行，大约 1 小时。**
其余全部由脚本准备就绪。下面每一步都可以照着敲。

---

## 一、为什么这一格不能自动化

评测分了四层，前三层都能机器算：

| 层 | 指标 | 数据从哪来 |
| --- | --- | --- |
| 工具层 | 工具序列、参数、步数 | Agent 的 trace，机器读 |
| 任务层 | 原因码命中率、引用率、处置建议率 | 从 `labels.json` 注入的退化类型**推导** |
| 解释层 | 相关性/准确性/完整性/有用性 | LLM-as-Judge 打分 |
| **决策层** | **审核结论正确率** | **只能由人标注** |

第四层卡在一点上：`pass / review / reject` 是「按监管口径，这条记录**应当**怎么处置」，
它取决于业务规则和风险偏好，**不是从图像退化类型能算出来的量**。

如果写段代码推一份「期望结论」再拿它当基准，等于让系统自己给自己打分：
数字会很好看，但它测的是「系统是否自洽」，不是「系统是否对」。
所以这一列必须是人填的 —— 这不是偷懒没做自动化，是**这一格本身的意义就在于它是人的判断**。

代码能做的是把手工业余量压到最小，把「翻样本、拼字段、对齐 id」这些机械活替你做掉。

## 二、操作步骤

### 第 0 步：确认环境

脚本和评测都在项目根目录 `J:\job\bank-ocr-test-platform` 下跑。

### 第 1 步：生成待填清单（一条命令）

```bash
python -m scripts.make_verdict_worksheet
```

它会产出两个文件：

- `data/annotations/review_verdicts_worksheet.csv` —— **你要填的表**
- `data/annotations/review_verdicts.json` —— 程序读的权威格式，`expected_verdict` 留空等你填

如果文件已存在，脚本会拒绝覆盖（防止你填了一半被冲掉）。确实要重来加 `--force`。

### 第 2 步：用 Excel / WPS 打开 CSV 填一列

表格长这样，**你只需要动倒数第三列**：

| sample_id | doc_type | 注入的退化类型 | 原因码 | 图片路径 | **expected_verdict_填这里** | key_reason_codes_可选 | note_可选 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| golden-bank_card-blur-00 | bank_card | blur | image_blur | data/processed/... | **(填这里)** | | |
| golden-bank_card-normal-00 | bank_card | normal | （无） | data/processed/... | **(填这里)** | | |

每行只能填三个值之一：

- `pass` —— 材料没问题，无需人工介入
- `review` —— 需要人工复核
- `reject` —— 直接拒绝

另外两列是可选的：`key_reason_codes` 填你认为**最关键**的原因码，
`note` 写一句判断依据（比如「模糊但字段可读，按重拍处理」）。

**判断依据已经摆在左边**：退化类型、原因码、图片路径都在同一行。
拿不准就打开图片路径看一眼实际图像。

### 第 3 步：抄回 JSON，补上署名

把填好的那一列抄回 `data/annotations/review_verdicts.json` 的 `records[*].expected_verdict`，
然后在文件**头部**填两个字段：

```json
{
  "version": 1,
  "annotated_by": "你的名字（岗位）",
  "annotated_at": "2026-09-15",
  "records": [ ... ]
}
```

**不确定填成什么样？** 看 `data/annotations/review_verdicts.example.json` ——
那是同一格式的【已填写样例】（3 条，结论是编的，别照抄），直观展示填好后长什么样。

这两个必填。没有署名的标注集在争议时无法复核，也就不能当基准 ——
所以脚本会**拒绝**一份没署名的标注，宁可报告里写「决策层不可用」。

### 第 4 步：校验

```bash
python -m scripts.evaluate_ai_review
```

对比一下前后就能看出标注生效了：

**填之前**，报告末尾是这样：

```
   · 决策层不可用：缺少 annotated_by（谁标的）、缺少 annotated_at（什么时候标的）（标注必须可追溯）。
   · 决策层不可用：40 条尚未填写 expected_verdict。
   · 决策层（真实审核结论正确率）本轮不计入：填好标注后重跑本命令即可启用。
```

**填够了之后**，会变成：

```
   · 决策层已启用：40 条样本带人工结论标注（你的名字（岗位），2026-09-15）。
```

任务层里会多出一行 `结论正确率`。

## 三、门槛：为什么 3 条不算数

脚本不让你一填完就出数字，有两个门槛：

- **至少 20 条**（`MIN_READY_SAMPLES`）
- **覆盖 golden 集的 50%**（`MIN_READY_COVERAGE`）

不够就仍按「不可用」处理，并在报告里说清是差在哪一条。

理由很直白：**一个基于 3 条样本的正确率，比没有数字更糟，因为它看起来像个结论。**
老板或面试官看到「结论正确率 66.7%」会当成一个结论去决策，
而这三个字背后的样本量根本不支持任何决策。宁可写「不可用」，也不要一个装饰性的百分比。

所以别只挑几条好填的填 —— 挑着填还可能让指标偏向某一类样本。**整批填完最省事也最可靠。**

## 四、常见问题

**Q：能不能先给我看一眼系统现在判的是什么，我对着填？**
能，但**不推荐**：`--with-reference` 会多输出一列「按原因码推导的结论」。

```bash
python -m scripts.make_verdict_worksheet --with-reference
```

一旦你看见「系统判的是 review」，你会不自觉地写 review，
这个基准就退化成「系统与自己的一致率」—— 数字很漂亮，但什么都没测到。
真要对照，等第一轮独立填完之后再比，那样差异才有信息量。

**Q：JSON 和 CSV 我该填哪个？**
CSV 是给你填着方便的，**JSON 是权威格式**。实在懒得抄，也可以只填 CSV，
但目前评测读的是 JSON，所以填完还是要把那一列搬回 JSON。

**Q：填错了怎么办？**
随便改。评测对格式错误是**降级不崩溃**：某一格取值非法，它会报出是哪一格、错在哪，
决策层标成不可用，其它三层照常跑。不会因为一个错字让整个评测跑不起来。

**Q：不太确定某条该 pass 还是 review 怎么办？**
写 `review` 并在 `note` 里注明你的犹豫。真实的审核场景里，
「不确定 → 转人工」本身就是正确处置；把犹豫记下来，比硬猜一个值更有价值。

## 五、跑完这轮之后

标注是评测的**输入**，不是一次性任务。后续有价值的方向：

1. **加样本**：golden 集上限 50 条，目前用来标注的是 40 条；补满能提高覆盖率。
2. **对比分歧**：把「人工结论」和「系统判定」的差异单独列出来，
   这些不一致的行才是真正值得分析的 —— 是规则漏了，还是标注口径有分歧。
3. **固化口径**：如果标注时反复纠结同一类情况（比如「轻微模糊算不算 review」），
   说明业务规则本身需要写清楚。这类反复出现的犹豫，就是规则文档该补的地方。
