# 真实模型多次采样评测：方法与首次结果（2026-10-04）

> 回答的问题不是「这条链路通不通」（那个由
> [`evaluate_ai_review.py --live`](../../scripts/evaluate_ai_review.py) 的单轮
> 验证回答），而是**「单点数字能不能信」** —— 项目自陈的头号弱点：
> 「真实模型只跑过一轮、只试过一个模型，单次采样不足以断言稳定性」。

## 一、方法

### 工具

新增 [`scripts/evaluate_live_sampling.py`](../../scripts/evaluate_live_sampling.py)，
机制在 [`ai_service/eval/sampling.py`](../../ai_service/eval/sampling.py)：

```
同一 golden 集 × 同一配置 × rounds 轮（轮间不共享任何 Agent 状态）
        ↓
逐指标给出 均值 / 样本标准差 / 极差 / 样本量 n
        ↓
多模型各跑一组 → 同一份报告里对照
```

### 关键设计

| 设计 | 理由 |
| --- | --- |
| **每轮重新构造 Agent** | 轮间共享状态就不是独立样本，方差会被系统性低估 |
| **单轮 stdev = null（不是 0）** | 输出 0 会让人以为「非常稳定」，事实是「没测方差」 |
| **某轮缺的指标不进分布** | 平均掉它等于假设那轮也测了 —— 两轮跑的不是同一个东西 |
| **n 写在每个数字旁边** | 没有 n 的均值不可解读 |
| **失败如实记录不吞** | 某个模型整组失败会写进报告，而不是悄悄少一列 |
| **key 只走环境变量** | 不写进任何文件、不进任何 commit；测试断言报告里不含 key |

### 预置模型按实测目录修正

2026-10-03 对 `GET /models` 的实测：DeepSeek 官方只开
**`deepseek-flash`** 与 **`deepseek-v4-pro`** 两个模型。
项目旧文档里的 `deepseek-chat` / `deepseek-reasoner` 已下线 —— 沿用旧名会
得到 400 而不是「模型不存在」，容易误判成配置问题。
这条已固化成测试 `test_preset_model_names_match_the_live_api_catalogue`。

## 二、结果

实跑：2026-10-04，`deepseek-flash` + `deepseek-v4-pro` 各 3 轮 × 40 条 golden，
全部轮次成功。完整数据：[sampling.json](../reports/live-sampling/20261004-121135-deepseek-flash-deepseek-v4-pro/sampling.json)。

### 摘要（只列最有解读价值的，n=3）

| 指标 | deepseek-flash | deepseek-v4-pro | 读法 |
| --- | --- | --- | --- |
| `task.verdict_accuracy` | 0.7250（stdev **0**） | 0.7250（stdev **0**） | **两模型三轮完全一致**，且与离线基线同值 —— 结论层由规则主导，不随模型漂 |
| `task.reason_code_match_rate` | 0.9250（stdev 0） | 0.9250（stdev 0） | 同上，原因码层也是确定性的 |
| `tools.parameter_accuracy` | 1.0000（stdev 0） | 1.0000（stdev 0） | 参数校验全过，两模型都严格守法 |
| `tools.tool_set_accuracy` | 0.8167（stdev 0.014） | 0.8000（stdev 0） | 选**哪几个**工具基本稳定 |
| `tools.sequence_accuracy` | 0.1000（stdev 0.043） | 0.2167（stdev 0.029） | 顺序匹配依然很低，且**v4-pro 更稳** —— 印证「顺序不是有效信号」的既有结论 |
| `explain.relevance` | 4.5083 | **4.7583** | 解释相关性 v4-pro 更高 |
| `explain.accuracy` | 2.5000 | **3.0500** | 解释准确性 v4-pro 明显更高（差距 0.55 > 各自 stdev） |
| `explain.completeness` | 3.8250 | 3.8000 | 基本持平 |
| `task.truncated_rate` | 0.0167 | **0.1500** | **v4-pro 截断率是 flash 的 9 倍** —— 推理模型更啰嗦，预算更紧 |
| `tools.avg_steps` | 3.45 | 3.56 | 步数接近，v4-pro 略多 |
| `cost.avg_provider_tokens` | 4160.75（±71.95） | 4172.45（±31.88） | token 用量两模型几乎相同 |
| `task.llm_failure_rate` | 1.0000 | 1.0000 | 见下方「三、解读边界」第 3 条 —— 是复核服务不可达，不是模型错误 |

### 三个真正有价值的发现

**1. 方差本身成了新信息 —— 而且它把「确定性层」和「模型层」干净地分开了。**

凡是 `stdev=0` 的指标（`verdict_accuracy` / `reason_code_match_rate` /
`parameter_accuracy`），两模型三轮**一个数都没动**。这印证了项目的设计立场：
**规则拥有否决权，模型只在解释层起作用** —— 结论层不随模型、不随采样波动。
反过来，`explain.*` 与 `tools.sequence_*` 有方差，才是真正「模型在起作用」
的地方。这个区分在单轮跑出来的数字里是**看不见的**。

**2. 两个模型在任务层打平，在解释层拉开差距。**

任务层（结论 / 原因码 / 参数 / 工具集）两模型几乎同分；解释层
`explain.accuracy` 差 0.55（flash 2.50 vs v4-pro 3.05），远超各自的
stdev（0.043 / 0.087）。**「换更好的模型」买不到更准的结论，但买得到更好的
解释** —— 这对「该在哪个环节花钱」是个直接的决策依据。

**3. v4-pro 的截断率是 flash 的 9 倍（0.15 vs 0.0167）。**

推理模型输出更长，同样的 token 预算下更容易被截断。若要生产使用 v4-pro，
需要单独调预算 —— 这正是「成本指标必须按模型分别看」的实例。


## 三、解读边界（先读这个再看数字）

1. **golden 集是合成的 40 条**。所有结论的适用范围是「本项目的合成集」，
   不代表真实证件分布下的模型能力。
2. **n=3 的 stdev 只能当方向看**。它回答的是「这个数字是不是纯粹靠运气」，
   不是「模型 A 显著优于模型 B」—— 后者需要远大于 3 的样本量，
   在这个量级上做显著性检验是伪精确。
3. **双判路径未参与**。AI 复核服务（127.0.0.1:8100）未启动，
   双判按设计回落规则原判（`llm_failure_rate` 因此为 1.0 —— 这是
   「复核服务不可达」，不是「模型判断错误」，两个信号要分开读）。
4. **成本口径**。`cost.avg_provider_tokens` 只覆盖 Agent 的 token 消耗，
   不能用它推断平台侧所有链路的模型费用。
5. **单次实验**。同一天、同一 key、同一网络环境。要断言「稳定」，
   需要跨天、跨时段重复整个实验。
