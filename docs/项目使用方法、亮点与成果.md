# Bank OCR Test Platform：使用方法、项目亮点与实际成果

> 更新日期：2026-09-28  
> 当前分支：`feature/user-admin-portal`  
> 项目定位：面向银行远程开户、信用卡进件场景的 OCR 审核测试平台  
> 当前验收：**1539 passed / 0 failed / 0 errors**

最新验收包含三个不同结论：自动化回归健康；45 条合成客服用例按严格闸门判据通过；**本轮真实 AI 服务与模型质量仍未验证**。不能把这三项合并称为“AI 全部通过”。完整证据见 [审查问题修复验证](审查问题修复验证.md)。

## 1. 项目简介

本项目实现了银行卡和身份证影像从上传到审核的完整测试链路：

```text
图片上传
  → 文件安全校验
  → 图像质量检测
  → OCR 文字识别
  → 结构化字段解析
  → 确定性规则审核
  → 审核记录落库
  → AI 审核解释 / 银行业务知识问答
  → 指标监控、离线评测与 CTE 测试演进
```

项目既可以作为普通 OCR 接口测试平台运行，也包含一套针对 Agent、知识客服和不确定性输出的测试方法。当前是测试开发与技术演示项目，不是生产级银行系统。

## 2. 主要能力

### 2.1 OCR 审核平台

- 银行卡审核：识别银行卡号、有效期和持卡人姓名；
- 身份证审核：自动判断正反面，解析姓名、性别、民族、出生日期、住址、身份证号、签发机关和有效期限；
- 图像质量检测：检测模糊、过暗、过亮、反光，以及文字倾斜和疑似深色矩形遮挡；
- 规则审核：输出 `pass`、`review` 或 `reject`，并提供稳定的原因码；
- 审核追踪：每次请求生成 `request_id`，结果写入 SQLite；
- 安全日志：银行卡号、身份证号写入日志前自动脱敏；
- 用户与管理门户：支持登录、角色权限、CSRF 防护、审核记录查询和详情查看。

### 2.2 AI 能力层

- 审核 Agent：通过只读白名单工具解释审核结论；
- 知识客服 Agent：回答公开业务规则、材料和办理流程；
- 多轮问答：调用方携带历史，服务端不保存会话；
- 合规保护：个人数据、征信、个性化建议和内部口径由出口闸门拒绝；
- 知识接地：没有知识依据时不生成事实性答案；
- 录制回放：真实模型交互可以录成 cassette，CI 离线复现；
- 故障降级：模型不可用、超时或返回非法内容时回到确定性结果；
- MCP 接入：通过本地 stdio 提供 `review_explain` 和 `knowledge_ask` 两个工具。

### 2.3 CTE 测试演进

CTE（Continuous Test Evolution）负责把一次真实失败转化为长期回归资产：

```text
Event → Blind Predict → Execute → Compare → Reflect
      → Candidate → Validate → Human Promotion → Validated Knowledge
```

CTE 不依赖大模型。事件回放、结果比较、验证矩阵、pytest 回归和人工晋级都是确定性流程。大模型以后可以用于辅助归因或起草测试，但不能修改 Ground Truth、Evaluator、安全不变式或自行宣布通过。

CTE 当前是命令行流程，不是自动运行的监控服务。用户授权的代码和评测修复由开发者完成；CTE 保留事件、验证和审批记录，不自行调整真值或批准候选。

## 3. 快速开始

以下命令均在项目根目录执行：

> 下面以 PowerShell 为主。普通的 `python`、`conda` 命令也可直接在 Windows CMD 中执行；CMD 切换盘符和目录时使用 `cd /d`，设置环境变量时使用 `set 变量名=值`。完整 CMD 命令见 [3.6 Windows CMD 命令汇总](#36-windows-cmd-命令汇总)。

```powershell
cd J:\job\bank-ocr-test-platform
conda activate bank
python -m pip install -r requirements.txt
```

### 3.1 创建登录账号

项目不提供默认明文账号。创建普通用户：

```powershell
python scripts/create_user.py --username demo-user --role user
```

创建管理员：

```powershell
python scripts/create_user.py --username admin --role admin
```

脚本会交互式要求输入并确认密码，数据库默认写入：

```text
reports/review_records.db
```

账号权限由数据库中的 `role` 决定，用户名叫 `admin` 不会自动获得管理员权限。创建账号时必须明确使用 `--role admin`。登录成功后，管理员跳转到 `/admin/reviews`，普通用户跳转到 `/user`。

创建脚本不会覆盖已有账号；如果提示账号已存在，应核对已有账号角色。创建账号与启动平台时应使用同一个 `REVIEW_RECORDS_DB_PATH`；未设置时均使用上述默认数据库。会话密钥保持不变时，服务重启不会要求重新登录。

### 3.2 启动主平台

默认使用 mock OCR，适合功能演示、接口测试和 CI：

```powershell
$env:OCR_MODE="mock"
python -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8001
```

常用入口：

| 入口 | 地址 |
| --- | --- |
| 登录页 | `http://127.0.0.1:8001/login` |
| 用户首页 | `嘻嘻嘻。吗 ` |
| 银行卡审核 | `http://127.0.0.1:8001/user/bank-card` |
| 身份证审核 | `http://127.0.0.1:8001/user/id-card` |
| 管理端审核记录 | `http://127.0.0.1:8001/admin/reviews` |
| Swagger 接口文档 | `http://127.0.0.1:8001/docs` |
| 兼容版银行卡页面 | `http://127.0.0.1:8001/bank-card/ui` |

生产部署应显式配置稳定、随机且保密的 `SESSION_SECRET`。本地未配置时，系统首次生成随机密钥并保存到 `reports/.session-secret`，后续启动、自动重载及同一项目的不同端口复用该密钥。该文件已加入 Git 忽略，不应提交或在清理报告时删除；显式配置的 `SESSION_SECRET` 始终优先。

如果上传图片或查看详情反复要求登录，先检查启动实例是否使用同一会话密钥和用户数据库。浏览器 Cookie 不按端口隔离，8001 与 8002 的同名 Cookie 会互相覆盖；不同密钥会使原登录失效。修改密钥、删除本地密钥文件，或首次应用此次修复后，旧 Cookie 会失效，需要重新登录一次。正常重启和自动重载不再清空登录状态，主动退出及会话到期仍需重新登录。

PowerShell 设置示例：

```powershell
$env:SESSION_SECRET="请替换为稳定的随机密钥"
```

Windows CMD 设置示例：

```cmd
set SESSION_SECRET=请替换为稳定的随机密钥
```

### 3.3 切换真实 PaddleOCR

默认 mock 模式不会加载真实 OCR 模型。使用真实 PaddleOCR：

```powershell
$env:OCR_MODE="paddle"
python -m uvicorn app.main:app --host 127.0.0.1 --port 8001
```

Windows CMD：

```cmd
set OCR_MODE=paddle
python -m uvicorn app.main:app --host 127.0.0.1 --port 8001
```

真实模式启动较慢，并可能需要单独准备 PaddlePaddle/PaddleOCR 模型。普通 pytest 和 CI 固定使用 mock 路径，不会下载模型。

切换模式前，先在原终端按 `Ctrl+C` 停止占用 8001 的平台进程，再在设置了 `OCR_MODE` 的同一个终端重新启动。环境变量不会自动传给另一个已经运行的进程。

重新上传一张图片后，在管理端查看**这条新记录**的“OCR 模式”，或查看对应 `request_id` 的 `ocr ... mode=paddle` 日志。旧记录继续显示创建时的 `mock` 属于正常行为。页面列名“OCR 模式”表示识别方式，实际值 `paddle` 才表示使用 PaddleOCR；它与 AI 服务的模型配置是两回事。

### 3.4 启动 AI 服务（可选）

另开一个终端：

```powershell
cd J:\job\bank-ocr-test-platform
conda activate bank
python -m ai_service
```

AI 服务默认监听 `http://127.0.0.1:8100`。不启动 AI 服务时，OCR、规则审核和记录查询仍可正常使用，只缺少 AI 解释能力。

无密钥启动服务时，解释和客服可以使用确定性检索、规则与模板；服务可访问不等于真实模型可调用。检查服务状态：

```powershell
Invoke-RestMethod "http://127.0.0.1:8100/health"
```

`status=ok` 表示服务可达，`llm_available` 表示模型配置是否可用，均不能代替一次成功的真实调用。

无需 API Key 的本地用法：

```powershell
python -m ai_service --demo
python -m ai_service --agent
python -m ai_service --search "反光了怎么办"
python -m ai_service --ask "办理二类账户需要哪些材料"
```

常用 AI 接口：

| 接口 | 用途 |
| --- | --- |
| `GET /health` | 健康状态、索引和工具清单 |
| `GET /metrics` | Prometheus 格式指标 |
| `POST /agent/explain` | 多步审核 Agent 解释 |
| `POST /knowledge/ask` | 银行业务知识问答 |

只有明确需要验证真实模型时才使用 `--live`：

```powershell
$env:LLM_PROVIDER="openai"
$env:LLM_BASE_URL="请替换为服务商的 OpenAI 兼容 API 地址"
$env:LLM_MODEL="请替换为模型名称"
$env:LLM_API_KEY="请替换为自己的 API Key"
python -m ai_service --agent --live
```

Windows CMD：

```cmd
set LLM_PROVIDER=openai
set LLM_BASE_URL=请替换为服务商的OpenAI兼容API地址
set LLM_MODEL=请替换为模型名称
set LLM_API_KEY=请替换为自己的APIKey
python -m ai_service --agent --live
```

`--agent`、`--ask` 等 CLI 演示默认走离线策略，显式加 `--live` 才使用配置的模型。**HTTP 服务和 MCP Server 不同**：它们会读取启动时的模型配置，配置了有效模型后，接口或工具请求可能触发真实调用。平台双判也可能请求 AI 服务，不能仅凭 CLI 未加 `--live` 判断整个系统没有模型调用或费用。密钥只放在自己的运行环境中，不写入文档、仓库或日志。

启动 HTTP 服务和执行 `--live` 评测的终端都需要模型配置；配置变更后应重启服务。本轮验收曾出现 `WinError 10061`、40 条审核 Agent 全部降级，说明当时没有完成真实 AI 验证；这不是当前服务状态的永久判断。

## 4. 典型使用方法

### 4.1 用户提交银行卡审核

1. 登录 `http://127.0.0.1:8001/login`；
2. 进入“银行卡审核”；
3. 上传合成测试图片；
4. 查看质量结果、OCR 文本、结构化字段、审核结论和原因码。

推荐正常样本：

```text
data/processed/bank_card/normal/bank_card_0001.png
```

异常质量样本：

```text
data/processed/bank_card/blur/bank_card_0001.png
data/processed/bank_card/dark/bank_card_0001.png
data/processed/bank_card/bright/bank_card_0001.png
data/processed/bank_card/glare/bank_card_0001.png
```

正常样本通常返回 `pass`；一般质量退化返回 `review`；严重模糊、严重过暗或严重过亮返回 `reject`。

退化目录名是测试样本的分类，不是审核指令。系统根据实际图像指标和字段执行规则；文件放在 `dark` 下，并不意味着它一定超过严重过暗阈值。

新增几何质量规则：

| 原因码 | 当前判据与处理 |
| --- | --- |
| `image_rotated` | 多个分散文字区域的倾角一致，绝对倾角超过 1°时转人工复核；也处理支持的侧向图像 |
| `image_occluded` | 检测疑似大块深色、低纹理矩形遮挡时转人工复核 |

这两项已加入质量检测和审核边界。AI 不能仅凭文字识别完整就把这类复核改成通过。遮挡检测目前不是通用物体识别：手指、浅色或纹理遮挡未充分覆盖；旋转检测也不保证识别所有方向，尤其不能据此保证 180°倒置一定检出。

### 4.2 用户提交身份证审核

进入“身份证审核”，分别上传正面和反面图片。系统会判断：

- `front`：正面字段；
- `back`：反面字段；
- `unknown`：无法可靠判断，需要人工复核。

接口分别为：

```http
POST /bank-card/review
POST /id-card/review
```

主要响应字段：

- `request_id`：审核链路唯一标识；
- `review_result`：`pass`、`review` 或 `reject`；
- `review_reasons`：最终审核原因码；
- `quality`：质量指标和质量原因；
- `ocr_text`：OCR 原始文本行；
- `fields`：结构化字段；
- `side`：身份证正反面判断。

### 4.3 管理员查看审核记录

管理员登录后访问：

```text
http://127.0.0.1:8001/admin/reviews
```

管理端支持：

- 按证件类型筛选；
- 按审核结论筛选；
- 按 `request_id` 查询；
- 查看质量原因、审核原因、OCR 模式和解析字段；
- 在详情页调用 AI 审核解释并查看 Agent 轨迹。

审核记录 API：

```http
GET /review-records/{request_id}
GET /review-records?doc_type=bank_card&review_result=review
```

记录查询接口需要管理员登录态。

### 4.4 提交失败时按 request_id 查日志

1. 复制结果卡片上的完整 `request_id`。身份证两面会分别提交，每面有独立 ID；不要混查。
2. 管理员进入 `/admin/reviews`，查询该 ID，先看错误状态、`error_message`、OCR 模式和原因码。
3. 若页面没有 ID，在浏览器按 `F12`，打开 Network，重新提交并查看 `/bank-card/review` 或 `/id-card/review` 的响应。对仍显示为“处理中”的请求，应等请求完成再判断。
4. 按 ID 搜索平台日志，依次定位 `file validation`、`quality check`、`ocr`、`field parse`、`rule check` 和 `review failed`，再查看异常栈。

本次本地排查使用的日志文件为：

```text
reports/test-artifacts/geometry-review/backend-live.log
```

PowerShell 查询示例：

```powershell
$requestId="请替换为完整 request_id"
Select-String -LiteralPath "reports/test-artifacts/geometry-review/backend-live.log" -SimpleMatch $requestId -Context 2,6
```

如果自行启动的新服务尚未保存日志，可使用本仓库已有的 INFO 日志配置启动，并将输出写到自己的日志文件：

```powershell
New-Item -ItemType Directory -Force reports | Out-Null
python -m uvicorn app.main:app --host 127.0.0.1 --port 8001 --log-config reports/test-artifacts/geometry-review/logging.json 2>&1 | Tee-Object -FilePath reports/backend.log
```

启动前停止原 8001 进程；上述 `logging.json` 是本次排查产物，使用前确认它存在。新日志按相同方式搜索 `reports/backend.log`。只看访问日志的 HTTP 状态码，通常不足以定位 OCR 或解析异常。

排查时区分三类结果：

| 表现 | 优先检查 |
| --- | --- |
| “未过规则校验”、`review` 或 `reject` | 看 `review_reasons` 与质量指标，属于审核结论，不一定是服务异常 |
| “未能识别有效期限”等缺字段 | 看 OCR 原文是否有有效字段证据，再区分 OCR 与解析器问题 |
| “图片处理失败”、HTTP 500 | 查 `error_message` 和服务异常栈；不能据页面文案直接认定是上传图片坏了 |

当前处理异常会尝试保存失败审核记录；旧版本未保存的历史 500 可能查不到，不能凭空补出当时的根因。

### 4.5 使用知识客服

CLI 示例：

```powershell
python -m ai_service --ask "银行卡丢失后应该怎么办"
python -m ai_service --ask "办理二类账户需要哪些材料"
```

正常公开业务问题会给出带知识依据的回答；个人征信、客户隐私、内部风控口径和个性化投资建议会被拒绝或引导到正式渠道。

## 5. CTE 使用方法

### 5.1 查看事件

```powershell
python -m scripts.run_cte --list
```

### 5.2 跑一条完整闭环

```powershell
python -m scripts.run_cte --event EVT-001
```

默认只跑到机器验证，不会自动晋级。

### 5.3 历史行为回放

```powershell
python -m scripts.run_cte --replay "我征信上有什么问题"
```

该命令会对比旧规则快照和当前行为，用于证明缺陷在修复前真实存在。

客服历史回放目前只覆盖规则层，不包含当时模型、Prompt 与完整服务运行状态。它证明的是旧判定逻辑，不能称为完整真实模型回放。已由用户提供结果的事件，其后续预测只针对固定版本重演；不能倒称为首次盲发现。

### 5.4 人工批准晋级

```powershell
python -m pytest -q
# 只有上一条全量回归通过、且本人授权署名后执行：
python -m scripts.run_cte --event EVT-001 --regression pass --approve jb
```

`NEW_TEST` 候选需要以下检查全部通过，并提供人工署名后，才能进入 `validated/`：

- `executable`：测试可以执行；
- `reproduces_before_fix`：修复前能够复现缺陷；
- `passes_after_fix`：修复后通过；
- `full_regression`：全量回归没有被破坏。

CTE 不会自行修改测试真值或自动批准。开发者根据 Candidate 编写回归测试和修复代码，再让 CTE 验证结果。

其他类型使用各自的验证矩阵，例如 `DOCUMENTATION` 要求有证据，并非所有候选都套用四项测试检查。`run_cte` 的 `--regression` 是调用方提供的结果，命令本身不会执行全量 pytest；即使参数默认是 `pass`，也不能代替真实测试输出。

### 5.5 OCR 快照录制与核验

该流程需要真实 PaddleOCR，不进入普通 CI：

```powershell
python -m scripts.record_ocr_snapshot --dry-run
python -m scripts.record_ocr_snapshot
python -m scripts.record_ocr_snapshot --verify
```

快照记录的是“系统实际观察到什么”，不是 Ground Truth。更新采用“录制 → diff → 人工审查 → 显式更新”，验证模式不会自动覆盖已有快照。

## 7. 项目亮点

### 亮点一：确定性规则掌握最终安全边界

项目没有把金融审核权直接交给大模型。规则结论为 `reject` 时，AI 不能放行；模型超时、不可用、输出非法或调用失败时，系统回到规则原判。AI 负责解释和有限增强，不负责无约束决策。

### 亮点二：测试 Agent 的过程，而不只测试最终文本

项目检查工具集合、调用顺序、参数、步数、token 预算、停止原因和异常降级。这样可以发现“答案看起来正确，但调用了错误工具或越过预算”的问题。

### 亮点三：模型交互可录制、可离线回放

真实模型和工具调用可以录制为 cassette。CI 使用固定回放，不联网、不需要 API Key，也不会因为模型随机性造成测试结果漂移。回放未命中会直接失败，不会偷偷访问真实模型。

### 亮点四：客服具有两道安全闸门

第一道闸门拦截个人数据、征信、内部信息和个性化建议；第二道闸门要求回答必须由知识库支撑。没有引用时宁可拒绝，也不编造营业时间、办理时效或统一额度。

评测同时检查“是否安全拒绝”和“是否由正确闸门拒绝”。EVT-007 证明，兜底保护生效时也可能存在边界分类缺陷，因此不能只看最终没有泄露。

### 亮点五：CTE 把真实失败变成长期资产

CTE 要求先做不可覆盖的盲预测，再执行、比较、复盘和验证。测试必须证明“修复前失败、修复后通过”，最后还需人工署名，避免系统通过修改答案或降低标准给自己打满分。

### 亮点六：用真实 OCR 观测检查字段解析

项目保留 2100 张合成图片的真实 PaddleOCR 输出。OCR 字段回放、归因报告和解析回归使用录制文本，与 `labels.json` 真值比较，暴露了 mock 输入掩盖的跨行解析、字符误识和标签误选问题。

这些验证使用历史 OCR 观测，不是每轮重新推理；也不能推广为所有 AI 链路都没有使用标签。本轮银行卡解析修复在 700 张快照上比较，保持原始 OCR、GT 和 baseline 不变。

### 亮点七：能够区分 OCR 责任和解析器责任

`missing_x` 本身只表示字段缺失。若同时存在 `evidence_missing_x`，说明当前证据检查没有找到该字段，应优先排查图像或 OCR；若原文有有效字段证据但解析结果仍缺失，才归为解析器没取到。不能仅凭一个 `missing_x` 就确定根因。该信号能减少把问题修错层的情况。

### 亮点八：对限制保持可验证的诚实

项目明确区分 mock 验证、真实 OCR 验证和真实模型验证；不把协议连通当成模型质量，也不把合成数据表现包装成生产效果。未解决问题继续保留，不通过降低断言让验收变绿。

## 10. 已知边界

- `EVT-006` 标签误选已修复；模糊姓名准确率 55%，残余漏字/粘连仍需 OCR 改善；
- 遮挡检测仅覆盖疑似深色矩形等支持的形状；旋转检测不保证 180°倒置或所有低纹理图像检出；
- 当前 AI golden 集没有纳入 occlusion / rotate，这两类由专门的图像规则回归验证，不能称为已经完成真实 AI 评测；
- 本轮 AI 评测 40 条全部降级；真实服务、真实模型质量和独立 Judge 校准尚需单独验证；
- CTE-003、006、007 仍为 `machine_validated`，无人工签名；`validated/` 仍只有原来的 4 条资产；
- 反光严重度暂不直接触发拒绝，需要产品口径和更多真实样本；
- 合成图片不能代表真实客户证件分布；
- 部分身份证号和有效期限低识别来自合成图水印遮挡，解析器无法恢复 OCR 没有输出的字符；
- SQLite 适合单机测试和演示，不适合生产级高并发存储；
- CTE 当前不是后台自动监控服务，事件需要登记或由外部 CI/人工流程导入；
- CTE 当前不会自动修改测试真值、业务代码或批准 Candidate，这些限制是可信性设计的一部分。
